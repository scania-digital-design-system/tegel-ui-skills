# Contributing to tegel-ui-skills

Anyone in the org can contribute — developer, designer, or project manager — using whichever AI tool you prefer (Claude Code or Codex). Both paths below are valid; pick the one that fits the situation.

## Path A — the easy one: `/tegel-skill-fix`

Use this when you spot the agent generating Tegel UI that drifts from the design system.

1. In your project, fix the bad UI by hand. Keep the fix in your working tree (don't commit yet — the meta-skill reads the diff against `HEAD`).
2. Invoke `/tegel-skill-fix` (or just tell the agent: *"the Tegel UI you generated was wrong, I fixed it — update the skill"*).
3. Answer the agent's questions about what was wrong and what you changed.
4. Review the proposed skill edit and the PR body the agent will open.
5. Approve. The agent opens a PR against this repo.
6. A maintainer reviews and merges.

Requirements: `gh` (GitHub CLI) installed and authenticated. If you don't have it, the meta-skill writes a patch file you can attach to a PR manually.

## Path B — the direct one: clone, edit, PR

Use this when you want to add new content, refactor a skill, or add a missing skill (e.g. `tegel-layout`, `tegel-typography`).

```sh
git clone https://github.com/scania-digital-design-system/tegel-ui-skills
cd tegel-ui-skills
# create a branch
git switch -c your-change-name
# edit skills/<name>/SKILL.md (or add a new skill folder)
# test locally — see "Local testing" below
# commit and push
git commit -am "what changed and why"
gh pr create
```

## What to edit, what not to edit

Each skill lives in `skills/<name>/SKILL.md`. The frontmatter (between the `---` lines) drives when the agent picks the skill up:

```yaml
---
name: tegel-something
description: One sentence describing WHEN to invoke this skill — phrases the user might say, or situations it applies to. The agent reads this to decide whether to load the skill.
---
```

Conventions:

- **`name`** matches the folder name exactly.
- **`description`** is invocation-focused. Write it like a trigger ("use when the user asks to X", "use when generating Y"), not like documentation ("this skill describes Z"). The agent uses these phrases to decide whether to load the skill at all.
- The first heading (`# tegel-something — short tagline`) matches `name`.
- An early section explains **when to invoke** in more detail than the frontmatter.
- Examples use markup the consumer can copy. Use Tegel tokens (`var(--color-foreground-text-strong)`, `var(--tds-spacing-element-08)`) — never hard-coded values.

Don't edit:

- Files under `bin/`, `package.json`, or `templates/AGENTS.md.tmpl` unless you're working on the installer itself.
- Files generated by the installer in a consumer project (`.claude/skills/`, `AGENTS.md`) — those are downstream copies. Always edit upstream here.

## Adding a new skill

1. Create `skills/<your-skill-name>/SKILL.md` with the frontmatter pattern above.
2. If the new skill belongs in the 6-step chain in `tegel/SKILL.md`, add it to that table.
3. If the new skill ships supporting files (a `.css`, a templates folder, per-component reference docs), put them in the same skill directory.

## Review checklist (for reviewers and authors)

Before opening / approving a PR, verify:

- [ ] Frontmatter has `name` and `description`. Description is invocation-focused.
- [ ] Every CSS variable referenced (`--color-...`, `--tds-...`, `--toggle-...`) actually exists in `@scania/tegel-lite`. Grep `node_modules/@scania/tegel-lite/dist/` if unsure. The `tegel-lite-setup` skill documents the most common false-friend tokens.
- [ ] Every class name (`tl-...`) exists. Same check, same dist directory.
- [ ] Example markup follows the BEM nesting documented in `tegel/components/<Name>.md`.
- [ ] No project-specific naming leaks in (no `site-*` classes, no consumer-specific assumptions).
- [ ] Cross-references between skills (e.g. `[tegel-spacing](../tegel-spacing/SKILL.md)`) resolve.
- [ ] If the change came from `/tegel-skill-fix`, the PR body includes the bad output, the user's fix, and the rationale.

## Local testing

Before opening a PR, install your branch into a throwaway directory and verify the agent can read it.

```sh
# From the repo root
npx --prefix . tegel-ui-skills --dest /tmp/test-consumer --check
```

`--check` prints what would change without writing. Remove `--check` to actually install, then open `/tmp/test-consumer` in Claude Code or Codex and try a prompt that exercises your change.

To run the installer directly without npx (faster iteration):

```sh
node bin/install.mjs --dest /tmp/test-consumer --check
```

## Code of conduct

Be kind, be specific, assume good intent. Skills are documentation — the bar for "good" is: would the next agent reading this generate correct UI? If a PR makes that more likely, ship it.
